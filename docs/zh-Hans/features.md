## 完整清单

**信号路径的比特精确是可以证明的。** 不是“我们觉得应该没有重采样”—— 是测出来的。
`yunaudio-cli selftest` 送一段 24 比特的伪随机序列走完整条路径，从 loopback 读回来，
从数据本身还原延迟，再逐个比对每个采样：

```
bit-exact: 261400/261400 samples identical, delay 872 frames
clock lock held at 0.999986 throughout
```

方法写在 **[MEASUREMENT.md](../../MEASUREMENT.md)** —— 序列是什么、为什么是 24 比特、
延迟怎么从数据里还原，以及同样重要的：这个测量**不能**证明什么。

之所以做得到，是因为 YunAudio 自己带一个虚拟设备，而不是借别人的。CoreAudio 驱动可以用
`GetZeroTimeStamp()` 定义自己的时钟，所以这一个把采样时钟推导自“该应用实际在捕获的那支
麦克风”。于是两个设备同步前进，HAL 的漂移校正可以关掉，路径上没有任何一段重采样。
第三方的 loopback 设备做不到 —— 它根本不知道你在意的是哪支麦克风。

那个 `0.999986` 是你麦克风的晶振误差，测出来的：慢了百万分之 14，折算成每小时 50 毫秒
的漂移 —— 如果没有人去校正它。

**而且这个检查你可以自己跑。** 它在“设置 → 诊断”里，不只在 CLI：按一个按钮，应用就把
序列送过你自己的路径，并给回来的结果评分。在没有时钟锁定的路径上，它会报出真实情况 ——
已重采样、还原出的 loopback 延迟、以及转换的幅度 —— 而不是通过或失败。

**它会告诉你路径的实话。** 比特精确、已重采样，还是已处理；实测的往返延迟；时钟锁定
当前有没有保持住。你一开人声隔离，它就会说出来，并停止声称比特精确 —— 因为处理信号和
“不动它”正好相反。

**响度按广播标准测。** 峰值表回答的是“会不会削波”。它回答不了任何在直播或录音的人真正
的问题，也就是“我和别人一样响吗”—— Discord 归一化到约 −18 LUFS、YouTube −14、广播 −23。
YunAudio 按 ITU-R BS.1770-4 测响度，那正是那些平台用的同一个标准：K 加权、400 毫秒块、
75% 重叠，以及那个让停顿不计入的两段式门。它读瞬时、短期与整体，然后把有用的那部分讲成
一句话 —— 你离所选平台还差多少，以及该往哪边调。

算术是对着标准检查的，不是对着自己：一个 1 kHz 正弦波读出的 LUFS 就是它自己的 RMS
电平、振幅加倍会恰好多 6.02、在 48 kHz 与 96 kHz 下读数相同、而段落之间的静音不会把它
往下拖。**macOS 上这个类别里没有别的软件测响度。**

**你可以从频谱上读出频率。** 二十四个对数间隔的频段，配一条频率轴，所以画面说的是
“是什么”而不只是“有多少”：60 Hz 的交流声、100 Hz 以下的桌面敲击、堆在 7 kHz 的齿音。
而且是校准过的，不只是排序过的 —— 一个已知振幅的音会以它自己的分贝值回来，那个断言在
这里抓到过一个真的变换错误。

**它会自己调平，而且知道自己在听什么。** 自动增益之所以有它现在的名声，只有一个原因：
包络跟随器分不出人声和电风扇，所以它把每一个停顿都用来把增益往房间噪声里推，然后在你
再开口时把你压下去。**它的问题在测量，不在控制环。**

YunAudio 一边按广播标准测响度，一边在同一份信号上运行 Apple 的端上声音分类器 ——
macOS 内置那个三百类的模型。调平器只在模型报告“说话”时移动，每秒 1.5 dB、在一个死区
之内、上限 15 dB。停顿、键盘声和空调不是关于“任何人有多响”的证据，所以它在那些时候
不动。界面会显示模型听到了什么，所以它是一份诊断而不是一个黑盒子：你声音下面出现
*打字* 就是该开门的理由。

那个控制环是一个没有任何依赖的值类型，配十三个测试 —— 因为一个“只被人对着麦克风讲话
试过”的调平器根本没有被测过：它必须收敛、不能过冲、不能来回振荡，而且要拒绝对着静音
动作。分类器是对着真的合成语音检查的，不是只对着它自己的标签表。

**KTV 不预设中文歌没有歌词。** 先用 Music 自己的歌词和本地 `.lrc`，再并行去问 LRCLIB、
QQ 音乐、网易云音乐和 lyrics.ovh。通过校验的时间轴胜出，并取消还在跑的较慢请求；简体
与繁体的元数据、现场版与电视演出的标记都会被比对，而不会把原唱错误地接到伴奏上。
Spotify 本身完全没有公开歌词属性，但一次真实运行 —— 黄霄云的《年少心动雨季》——
通过中文来源找到了一份 265 秒、超过六十行的时间轴。

评分会说出它的参考是什么。同名的 MIDI 文件是精确旋律；捕获到的原唱是自动的、从音频推导
出来的参考；而伴奏本身只能诚实地提供调性、音准和乐句时值，因为它不含人声旋律。每支
麦克风保有自己的音高历史与分数，所以对唱是**两份实际测到的演唱**，而不是从一份混音里
猜出两个人。Music 和 Spotify 通过它们的 scripting dictionary 提供受支持的 now-playing
元数据。其他被捕获的播放器，在分发用的 App ID 启用了 ShazamKit 服务时，走公开的
ShazamKit 识别；ad-hoc 构建会直接说出那个签名要求，而不是去重试一个注定不会成功的目录
请求。

**直接监听是真的直接。** 通过通讯软件听自己会慢三十毫秒，那已经足以让人说话打结。
这里的监听是同一个聚合设备上的第二个目的地，所以它是一个 IO 周期加上输出设备本身 ——
测到进显示器的音频是 11.2 毫秒，进任何驱动正常的设备是 2.7 毫秒。它**不受总推子影响**，
因为总推子是送给对方的电平，把它拉下来不应该让你听不见自己的声音；但输入电平和静音
**会**影响它，因为把麦克风静音本来就应该让你听不到它。两条规则都是直接对着实时回调
断言的。

**变声器改变的是声音，不只是音高。** 移调会把整个频谱一起搬 —— 基频，以及叠在它上面的
喉腔与口腔共振 —— 而耳朵把那读成“一颗比较小的头”，不是“另一个人”。这就是为什么每一个
移调器都做出花栗鼠。一个高大的男人和一个娇小的女人可以唱同一个音；不同的是他们的共振峰
落在哪里。

所以共振峰是独立移动的，那是 macOS 上没有任何东西提供的，这里从头写出来：从对数频谱的
低 quefrency 部分估出频谱包络、沿频率轴拉伸、再除回去，让谐波 —— 因此也让音高 ——
留在原来的位置。测试会断言这件事的**两半**，因为一个只检查“共振峰有动”的测试，对一个
普通的移调器也会通过。旁边还有一个音色阶段，用环形调制、抽取与软削波做出来：机器人、
无线电、怪物、数字破碎、外星人。

**变声要是一个声音，不是两个旋钮。** 音高和共振峰是分开的阶段，因为它们是分开的物理
事实 —— 但没有人想被告知这件事，他们想要的是听起来像另一个人，而那是一组**特定**的设置。
成年男性的说话音高大约在 110 到 130 Hz，成年女性大约 200 到 220，差不多是一个五度；
但只移五度的音高听起来明显就是处理过的，因为共振峰没有跟着动。女性的共振峰大约高
15 到 20 个百分点，来自一条大约短了那么多的声道。两者一起移，耳朵就不再听到“效果”。

这些预设是测出来的，不是宣称的：一个合成的男声通过“变高”预设，出来时音高上升了所声称
的 500 音分，而且频谱重心跟着一起上升 —— 同一份信号、走真实的处理链。

**它不是**神经网络的声音转换。像 fish-speech 或 RVC 那样的东西是学一个目标说话人再重新
合成，那是另一件事、而且是更好的一件事 —— 但它需要一个模型、一条 GPU 流程，以及远超过
一百毫秒。那些没有一样塞得进 2.7 毫秒的 IO 期限。今天发布的每一个实时变声器做的都是
这里做的事；这一个把它说出来。

**转录知道哪句是谁说的，而且不用猜。** 每一个做对话转录的产品都会在说话人分离这件事上
公开地留保留 —— 因为从声音里推断“谁在说话”是一个猜测，而且错得够频繁，足以成为人们
抱怨的那件事。

这个应用程序没有那个问题，而且**不是因为它解决了它**。麦克风是一个来源，每个被捕获的
应用程序是自己的一个 process tap，在任何东西到达模型之前就已经分开了。每个来源一个
转录器，而说话人标签是**接线**，不是推论。`SpeechTranscriber` 是 macOS 自己的模型，
设计给持续数小时的转录而不是短查询，而且它运行在设备上：没有按分钟计费、没有上传、
没有密钥。

**第三方 Audio Unit。** 这才是音频领域里“插件”的意思，而它也是唯一一个“加载别人的代码”
是正确答案、而不是一种绕远路避开配置文件的地方：格式本来就存在、系统会审查并沙箱它、
而且已经有几千个装在机器上了。它们插在一个位置，而那个位置不是随便选的 —— 在这个应用
所有塑形之后、限制器之前，因为限制器的整个工作就是“不让下游看到任何需要削掉的采样”。
任何运行在它之后的东西都能把信号重新推过满刻度，所以不论用户怎么拖，插件都不能被允许
放在那里。

一个必须运行在自己进程里的单元，会让每一次 render 变成一次 XPC 往返 —— 那在混音工程里
没问题，在一个期限 2.7 毫秒的回调里就不行。这件事会在它进入路径**之前**就讲清楚，而不是
事后才发现。

**设备是用文档描述的，不是用代码。** CoreAudio 会说一支麦克风有三个输入声道，然后对
“那三个上面是什么”一句话也没有。要知道 Seiren V3 Pro 的三个分别是“处理后的音头”、
“干的音头”和“麦克风自己扩展器的输出”，得把那东西拆开来看 —— 而那份知识以前是编译进去
的，所以每一支新麦克风都意味着一次代码改动和一次发版，只为了一张字符串表。现在它是一个
JSON 文件，而任何放进
`~/Library/Application Support/YunAudio/Devices` 的东西都会被叠加加载。

**故意是数据而不是插件**：一份配置描述硬件，它不执行；而从一个文件夹加载代码会意味着
签名、版本管理、稳定的 ABI，以及一个坏掉的文件有办法把音频系统一起带下去。

**来自 Apple 自家模型的人声隔离。** `AUSoundIsolation` 就是 FaceTime“人声隔离”背后的
那个模型，在设备上运行、免费，而这个类别里没有别的路由器把它当成通用的麦克风处理器
公开出来。这里测到：增加 56 毫秒延迟，CPU 用掉不到 IO 期限的四分之一。

**两级增益，顺序是对的。** 麦克风自己的增益发生在硬件里、在它的转换器之前，所以把它
调高不占用任何动态余量；而之后的数字电平只能放大转换器已经决定好的东西，包括噪声。
两者都在这里，而硬件那一级在前面 —— 那才是有意义的顺序，也是 macOS 上没有别的软件摆在
你面前的顺序。

它只在设备公开了可设置的增益时才出现，而“哪些设备是那些”这件事花了两次才问对。这里
最初的答案 —— 而且逆向工程的记录也同意 —— 是 Seiren **V2 X** 公开了一个、而
**V3 Pro 没有**，所以在 V3 Pro 上只剩数字电平。**那是错的。** CoreAudio 是**按 element**
公开一个设备的控件的，master 是 element 0，而只问 master 看起来像是可以用，因为多数设备
就在那里回答。V3 Pro 回答在 **element 1、2 和 3** —— 一个音头 tap 一个 —— 每一个都带着
它固件所记载的完整 **0 到 +36 dB**。没有人问对 element。

**零延迟监听，由麦克风自己做。** 同一次清查翻出一件 macOS 上没有任何东西提供去移动的
东西：Seiren 公开了一个 play-through 电平，那是设备在硅片里把自己的输入送回自己的耳机
孔。那才是麦克风包装盒上“零延迟”真正的意思 —— 信号从来没有到达电脑。这个应用程序自己
的监听是 2.7 毫秒，那很好，但不是零。Razer 的软件在 Windows 上通过一个 USB 请求碰到它；
这里没有 Synapse，而在此之前根本没有任何办法移动它。

它是被**提供**而不是被**开启**的，因为返回的是**未经处理**的音头：这里的任何处理都不
可能在里面，因为那些还都没有发生。

**它知道你麦克风的那些声道到底是什么。** CoreAudio 报告 Seiren V3 Pro 有三个输入，
然后对上面是什么一句话也没有。它们是处理后的音头、干的音头，以及经过麦克风自己扩展器
之后的音头 —— 那个扩展器位于转换器之前，所以它在任何东西可能削波之前就先去掉房间噪声。
选择器会把三个都命名，并说出每一个是做什么的。那份对应是从设备自己的模块转储它的内部
拓扑得来的，而 macOS 上没有别的东西会告诉你。

**设备被拔掉时它会继续。** 一支通话中掉出来的 USB 麦克风，以前会让路由器停下来等。
它现在会换到“最近用过、而且确实在场”的那支麦克风，说出它正在代替哪一个设备，并在原来
那支被插回去的那一刻换回去 —— 除非你在这期间自己选了别的，那会终止这个接管，因为那时候
把你换回去是在推翻一个决定，而不是在撤销一个意外。

**捕获应用程序音频不需要额外驱动。** 通过 `AudioHardwareCreateProcessTap` 捕获任何应用
程序，并且可以选择同时把它原本的输出静音。Loopback 和它的同类为了这件事需要自己的插件；
这里它是一个有文档的 API。

**它运行起来几乎不花什么。** 128 frame 下的立体声路由用掉单核心的 0.40%、常驻 4.7 MB
—— 那是测六分钟测出来的，不是估的。

**实时路径不做任何内存分配。** 是验证过的，不是宣称的：分配器上挂了一个钩子，计数任何
在 IO 线程上分配的东西。在优化构建下、数千个周期里是零。（要测 release 构建 ——
debug 构建自己的边界与独占性检查会分配内存，而那跟发布的代码无关。）
